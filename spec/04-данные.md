# 04. Данные и хранилище

## Разделение по частоте записи, а не по типу

Первая редакция спеки объявляла источником правды файлы целиком. Это ломается
на конкуренции: `plan.json` пишут Стратег, Редактор (статус `draft`),
Публикатор (`pub`) и Ресёрчер (метрики). Без блокировок два обновления подряд
теряют друг друга, а на синхронизируемой папке ещё и рождают
`plan (conflicted copy).json`.

Правильная граница — **как часто запись и кто пишет**:

| | Что | Формат | Пишет | Правда |
|---|---|---|---|---|
| **Холодное** | `core.md`, `goals.md`, `platforms.md`, `sources.md`, `design/` | markdown | человек и роли, редко | ✅ файл |
| **Горячее** | план, статусы тем, публикации, метрики | таблицы | код, постоянно | ✅ база |
| **Артефакты** | тексты постов, макеты, PNG | файлы | одна роль, один раз | ✅ файл |

`plan.md`, `plan.json` и `stats.csv` **становятся выгрузкой из базы**, а не
источником. Перезаписываются целиком после каждого изменения, читаются
человеком. Правка их руками ни на что не влияет — об этом надо сказать прямо
в шапке каждого файла.

Холодные файлы остаются правдой: человек должен уметь открыть `core.md` и
поправить голос руками, и там нет конкурентной записи.

> ⚠️ **Папка брендов не должна лежать в синхронизируемом облаке, пока бот
> пишет.** Клиент синхронизации читает файл в момент записи и плодит
> конфликтные копии.

## Где живут бренды

Рабочая папка бота — **в git, рядом с кодом**. Выгрузка в Nextcloud
односторонняя, для чтения человеком, раз в день или по команде.

Версионирование даёт то, чего не было: видно, когда и как менялось ЯДРО, и
можно откатить неудачную правку голоса.

### Правило одного владельца

Скиллы `brand-content-pipeline` остаются в работе параллельно с ботом. Значит
у одних и тех же файлов появляются два писателя, и это опаснее облачной
синхронизации: конфликт не будет виден вообще, просто одна версия перезапишет
другую.

**У каждого бренда ровно один владелец, и он записан явно.**

| Бренд | Владелец | Где |
|---|---|---|
| MAUNA | скиллы `brand-content-pipeline` | Nextcloud `Content factory/Brands/` |
| Тест | бот | git `content-factory/Brands/` |
| дальнейшие | бот | git |

Разделение **по брендам, а не по папкам**: два инструмента никогда не трогают
один бренд. Пока бот не заменит скиллы, MAUNA живёт по-старому и в git не
копируется.

Смена владельца — разовая операция руками: скопировать папку, поменять строку
в реестре, больше не трогать старое место. Держать бренд в двух местах
«на всякий случай» нельзя: разъедутся за неделю.

Реестр в `tenants.brand_folder` плюс строка `owner:` в шапке `core.md` —
чтобы это было видно и человеку, открывшему файл.

## Папка бренда

Структура уже обкатана на MAUNA в `Content factory/Brands/`. Не меняем.

```
Brands/{Бренд}/
├── core.md                    ЯДРО: кто, аудитория, позиционирование,
│                              линейка, каналы, воронка, банк CTA,
│                              голос, ценности, стоп-лист
├── goals.md                   цели, метрики, точка А → Б, проверка
├── platforms.md               нормы площадок
├── stats.csv                  лог публикаций
├── sources.md                 конкуренты и источники ресёрча
├── plans/
│   ├── 2026-08-18-plan.json   источник правды
│   └── 2026-08-18-plan.md     он же для чтения человеком
├── posts/
│   ├── 2026-08-18-tg-01.md            текст
│   ├── 2026-08-18-tg-01-cover.html    макет
│   └── 2026-08-18-tg-01-cover.png     готовая карточка
├── research/
│   ├── 2026-W33.md            дайджест недели
│   └── reels/mechanics.md     библиотека механик
├── voice-samples/             реальные тексты для калибровки
├── photos/                    фотобанк + index.json
└── design/
    ├── brand-core-design.md   палитра, шрифты, отступы
    ├── platforms/telegram.md  ТЗ формата
    └── assets/reference/      эталонные макеты
```

### Что читает какая роль

| Роль | Читает |
|---|---|
| 🔍 Ресёрчер | `core.md` (ниша, аудитория), `sources.md`, `stats.csv` |
| 🎯 Стратег | `core.md` (аудитория, воронка, банк CTA, каналы, линейка, стоп-лист), `goals.md`, `stats.csv`, `research/`, `plans/` |
| ✍️ Редактор | `core.md` (голос, био, ценности), `platforms.md`, `voice-samples/` |
| 🎬 Reels | `core.md` (`voice.spoken`), `research/reels/mechanics.md` |
| 🎨 Дизайнер | `design/`, `photos/index.json` |
| 📤 Публикатор | `platforms.md`, `plans/`, `credentials` из базы |

**Правило чтения: одна роль — один запрос — одна площадка.** Все ТЗ разом не
грузятся, это экономия контекста.

### Три файла, потому что три скорости

| Файл | Меняется |
|---|---|
| `core.md` | редко, раз в квартал |
| `goals.md` | каждый квартал |
| `stats.csv` | каждую неделю |

Смешать их в один — значит перечитывать всё ради одной цифры.

### ЯДРО это краткая стратегия

Две-четыре страницы, которые заменяют двадцатистраничный документ. Не для
чтения, а как рабочий вход для ролей. Тринадцать разделов, как в MAUNA:
кто · идея · аудитория · позиционирование · линейка · каналы · воронка ·
банк CTA · голос · визуал · ценности · стоп-лист · главная идея.

**Версионируется обязательно.** Человек будет менять ЯДРО, и надо понимать,
каким конфигом сгенерён каждый пост.

## Что появляется после онбординга

Папка создаётся при первом подтверждённом блоке, а не в конце. Путь:

```
content-factory/Brands/{slug}/
```

### Имя папки

Берётся из названия бренда, которое человек назвал в O1, приводится к slug:
`Лили Космос` → `lily-kosmos`. Занято — добавляется суффикс `-2`.

**После создания slug не меняется никогда**, даже если бренд переименовали:
на нём завязаны пути ко всем артефактам. Отображаемое имя живёт отдельным
полем в `core.md`.

### Что пишется на каком шаге

| Файл | Появляется | Собирает |
|---|---|---|
| `voice-samples/*.md` | O4–O5, сразу при получении | Редактор |
| `photos/` + `index.json` | O7 и дальше по мере присылки | Дизайнер |
| `core.md` | **после O8**, когда человек подтвердил ЯДРО | Ресёрчер собрал, Ассистент зафиксировал |
| `goals.md` | после O10–O12 | Стратег |
| `platforms.md` | после O13–O15 | Редактор и Дизайнер |
| `design/brand-core-design.md` | O15 | Дизайнер |
| `stats.csv` | при создании папки, пустой с заголовком | — |
| `plans/`, `posts/` | пустые папки | — |
| `sources.md` | отложено, при первом ресёрче | Ресёрчер |
| `design/assets/reference/` | первый удачный макет становится эталоном | Дизайнер |

**Правило: файл пишется только по подтверждённому блоку.** Черновик ЯДРА до
нажатия «верно» живёт в `onboarding.raw_inputs_json` в базе. Иначе на диске
лежал бы полуфабрикат, неотличимый от готового профиля, и следующая роль
взяла бы его в работу.

Бросил онбординг на середине — на диске нет ничего лишнего, в базе есть весь
прогресс, возврат с того же шага.

### Вложения от клиента

Фото, PDF, экспорт канала, голосовые.

> ⚠️ **`file_id` нельзя хранить как единственную ссылку.** Он привязан к
> конкретному боту и не гарантирован во времени. Всё присланное скачивается
> и лежит файлом, `file_id` — только кэш на повторную отправку.

| Что | Где | Сколько живёт |
|---|---|---|
| Фото | `photos/` | постоянно, они нужны Дизайнеру |
| Документы (PDF, экспорт) | `sources/uploads/` | постоянно |
| Голосовые | транскрипт в `onboarding.raw_inputs_json` | постоянно |
| Оригиналы голосовых | `tmp/voice/` | 30 дней, потом удаляются |

Транскрипт хранится всегда: после правки промпта распаковку можно
переизвлечь, не спрашивая человека заново. Сам звук для этого не нужен.

## Как клиент получает свои файлы

В коробке профиль клиента лежит **на сервере продукта**, а не у него. Открыть
`core.md` в редакторе он не может. Значит нужны три вещи, иначе продукт
непродаваем:

| Команда | Что делает |
|---|---|
| `покажи ядро` | Ассистент шлёт `core.md` документом в чат |
| `выгрузи всё` | zip со всей папкой бренда |
| `удали мои данные` | подтверждение в два шага, затем папка и записи в базе стираются |

Выгрузка обязана быть в человекочитаемом формате: клиент должен иметь
возможность уйти с ним к другому подрядчику. Это и честно, и снимает главное
возражение при продаже.

## Схема темы плана

```json
{ "id": "2026-08-18-tg-01",
  "date": "2026-08-18",
  "plat": "tg",
  "format": "пост",
  "rubric": "Приём недели",
  "goal": "warm",
  "arch": "Практика: промпт",
  "funnel_stage": "интерес",
  "cta_id": "cta-interest-01",
  "title": "Что я делаю с брифом до того, как открыть Claude",
  "hook": "Клиент прислал четыре строки. Я потратила сорок минут.",
  "why": "не знаю, с чего начать",
  "angle": "Кейс из работы",
  "charge": "recognition",
  "src": "plan",
  "status": "idea",
  "asset": "posts/2026-08-18-tg-01.md",
  "link": "",
  "core_version": "2026-08-13" }
```

### Идентификатор

`ГГГГ-ММ-ДД-площадка-NN`

**После создания не меняется никогда.** По нему связаны тема, текст, визуал и
метрики, и на нём держатся правки человека в дашборде. Новый id — правки
потеряны.

### Статусы

```
idea → draft → ready → pub
                    ↘ skip
```

| Статус | Значит |
|---|---|
| `idea` | утверждена, текста нет |
| `draft` | текст написан, не утверждён |
| `ready` | утверждено, ждёт публикации |
| `pub` | опубликовано, есть `link` и `external_id` |
| `skip` | не вышло. **Причина обязательна**, показывается в блоке «осталось в плане» |

### Значения полей

| Поле | Значения |
|---|---|
| `plat` | `tg` · `ig` · `yt` |
| `goal` | `warm` прогрев · `prod` продукт · `pers` личное |
| `src` | `plan` от стратега и согласовано · `adhoc` внеплановая просьба |
| `charge` | surprise · curiosity · humor · controversy · recognition · useful discovery · «а что, так можно было?» · anti-FOMO · cognitive dissonance · relatable pain · transformation |

## Статистика: две таблицы, а не одна

В первой редакции колонки `views_24h / 72h / 7d` соседствовали с колонкой
`window` — это противоречие: либо строка на пост, либо строка на снимок.
Разделяем.

**`metrics` — строка на снимок.** Сюда пишет сборщик.

```sql
metrics(post_id, window, collected_at, views, reach, likes,
        comments, saves, shares, watch_pct, subs_delta, source)
PRIMARY KEY (post_id, window)
```

`window` это `24h` · `72h` · `7d` · `30d`. Повторный сбор того же окна
перезаписывает строку, а не добавляет вторую.

**`stats.csv` — строка на пост, выгрузка для человека и для Стратега.**

```
post_id, date, platform, format, goal, funnel_stage, cta_id,
views_24h, views_72h, views_7d, reach, likes, comments, saves, shares,
watch_pct, subs_delta, source
```

`funnel_stage` и `cta_id` — то, чего в обычной аналитике нет и что даёт
главный разрез: **какой этап воронки просел**. Без них статистика показывает
«что залетело», с ними — «где течёт».

`source` описывает, откуда снята выгрузка и чего в ней нет. Смешал охват из
одной выгрузки с лайками из другой — обязан это написать.

**Поле, которого в выгрузке нет, не выставляется в ноль.** Ноль означает
«реально ноль», отсутствие означает прочерк.

## База

Только то, что нужно боту. **Схема живёт в `storage/db.py`** — здесь была
её копия, и она разъехалась: обещала таблицы `tasks` и `credentials`,
которых нет, и колонку `brand_folder`, которая называется `brand_slug`.
Схему читать в коде, а причины — здесь.

Таблицы: `tenants`, `topics`, `themes`, `posts`, `metrics`, `onboarding`,
`llm_usage`.

**Почему поля такие.**

- **`tenants.tz`.** Расписание «пятница 10:00» без часового пояса не
  имеет смысла. Дефолт `Europe/Moscow`.
- **`topics.topic_id` бывает `NULL`.** У General нет `message_thread_id`,
  и при отправке параметр не передаётся вовсе. Передать `1` — промахнуться.
- **`posts.external_id UNIQUE` и `attempts`.** Защита от двойной
  публикации: строка пишется со статусом `sending` **до** отправки, и
  процесс, умерший между отправкой и записью, при повторе упрётся в
  строку, а не создаст второй пост.
- **`themes.skip_reason`.** Пропуск без причины через месяц выясняется по
  необъяснимой дырке в статистике.
- **`themes.asset`.** Один путь на тему: текст поста, а для роликов —
  чистый суфлёр. Разбор лежит рядом отдельным файлом и в базу не идёт.
- **`onboarding.raw_inputs_json`.** Хранить не только извлечённое, но и
  сырое: иначе после правки промпта переизвлечь профиль невозможно.
- **`llm_usage`.** Потолок вызовов на тенанта в сутки. Круги переделки
  ограничены двумя, но цикл может закольцеваться иначе, и упереться
  лучше в счётчик, чем в счёт.

Статус `failed` дополняет `idea → draft → ready → pub | skip`: три
неудачные попытки — и человеку уходит причина. Молча терять задачу
нельзя, он ждёт пост.

**Токены в базе не лежат.** Только ссылка на секрет-хранилище.

## Валидаторы

Четыре скрипта. Детерминированная проверка вместо самооценки модели — самое
ценное, что нашлось в прототипе `brand-content-pipeline`.

| Скрипт | Что проверяет | Когда |
|---|---|---|
| `funnel_check.py` | реалистичность цели по выручке: какая доля базы должна конвертироваться | онбординг, пересмотр целей |
| `growth_check.py` | сколько охвата на пост нужно, чтобы цель по подписчикам сошлась | онбординг, раз в месяц |
| `validate_plan.py` | пустые поля, дубли id, CTA не из банка, доля тем в узкое место | перед выдачей плана |
| `check_voice.py` | **только регуляркой:** длинное тире, стоп-слова бренда, «не X, а Y», капслок, список усилителей | перед выдачей текста |
| `check_bundle.py` | комплект, совпадение id, guardrails, свободный слот, живой токен | перед публикацией |

### Граница детерминированного и модельного

Скриптом ловится только то, что описывается шаблоном: символ `—`, слова из
списка, конструкции `не … , а …`, `дело не в … , дело в …`, капслок длиннее
трёх букв, усилители из фиксированного перечня.

**Драматизация, симметричные фразы, абзацы-бантики и обобщённые персонажи
регуляркой не ловятся.** Это остаётся самопроверкой Редактора внутри промпта.
Делать вид, что валидатор закрывает всё — самообман: он пропустит именно
то, ради чего затевался анти-AI блок.

Правило простое: **скрипт даёт отказ, модель даёт предупреждение.** Отказ
блокирует выдачу, предупреждение попадает в лог рядом с текстом.

### Что считает `growth_check`

```
нужен прирост:        1966 подписчиков за 92 дня
постов за период:     3/нед × 13 недель = 39
прирост на пост:      50 подписчиков
при конверсии 2%:     нужно 2500 охвата на пост
текущий охват:        300 (из stats.csv)
вывод:                цель требует роста охвата в 8 раз
                      → узкое место это дистрибуция, а не контент
```

Такой вывод меняет весь план: если узкое место дистрибуция, Стратег ставит
коллаборации и посевы, а не «ещё больше полезных постов».

### Баланс воронки

**Основной механизм — узкое место**, считается кодом из `goals.md` и
`stats.csv`. План собирается под него, а не размазывается ровным слоем.

**Запасной — фиксированные 60/20/20** (прогрев / продукт / личное). Работает
первые три недели, пока статистики нет.
