# Стенд

```bash
./.venv/bin/python tests/run.py           # офлайн, бесплатно, ~2 минуты
./.venv/bin/python tests/run.py --live    # плюс живые вызовы модели
```

## Два вида циклов

**Офлайн.** Модель подменяется заготовленным ответом. Проверяется поведение
кода: ветки кнопок, запись в базу, границы, отказы. Гоняются перед каждым
коммитом — они быстрые и ничего не стоят.

**Живые** (`*_live_*`). Проверяют то, что подменой не поймать: соблюдает ли
модель формат, не режет ли валидация настоящий ответ, читается ли кеш
префикса на повторном вызове. Стоят денег и минут, поэтому отдельно.

Правило, оплаченное на практике: **после каждой правки валидации нужен
живой прогон**. Ужесточили проверку, поймали все кривые случаи и заодно
начали резать нормальный ответ, потому что модель ставит поле чуть иначе.
Тест «живой план ничего не потерял на валидации» существует ровно для этого.

## Изоляция

`harness.setup()` копирует базу и папку бренда в `.sandbox/`, и там же
чистит производные данные: темы, посты, метрики, счётчик вызовов, файлы в
`posts/` и `plans/`. Профиль тенанта остаётся.

Без чистки тесты начинают падать от чужой работы: бот за день пишет в
боевую базу свои темы, и цикл, который считает их количество, разваливается.
Это уже случалось.

Боевые данные стенд не трогает: всё в копии.

публикацию, и намеренно ломающийся, чтобы проверить `failed` и счётчик
попыток.

## Как добавить проверку

```python
check("что проверяем", условие, "что показать при провале")
```

Формулируй по тому, что ломается, а не по тому, что вызывается: не
«вызвался `_fit`», а «дата вне окна не записана». Тест, названный по
внутренностям, переживает поломку и молчит.
