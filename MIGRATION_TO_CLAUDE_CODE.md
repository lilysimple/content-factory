# Миграция на Claude Code Subagents

Статус: **этапы 1–5 пройдены, на этапе 6 собран MVP моста.** Ничего в
рабочей цепочке не изменилось: Telegram-боты по-прежнему ходят в Anthropic
API напрямую через `orchestrator/agent.py`, ни одна точка вызова не
удалена. Мост висит на отдельной команде `/plan` и ничего не перехватывает
у старого пути — по нему пока не прошло ни одной живой задачи до конца.
Документ фиксирует, что есть сейчас, куда идём и в каком порядке это
можно сделать, не сломав завод по дороге.

Два факта, выясненных замером, а не рассуждением (раздел 9).

**Bridge работает по подписке.** Разовый `claude` → `/login` в терминале
кладёт учётные данные в Keychain, подпроцесс берёт их сам, и
`ANTHROPIC_API_KEY` в его окружении не нужен. Зависимости от баланса API,
из-за которого завод простаивал, у нового пути нет.

**У каждого вызова есть двойной пол: около $0.11 API-эквивалента и 5–7
секунд.** И то, и другое не зависит от сложности задачи, это цена
холодного старта. Для «собери план недели» незаметно, для реплики в чате
это пауза, после которой человек считает, что бот сломан. Отсюда правило:
через bridge идёт оркестрация нескольких ролей, а запросы вроде «что
сейчас в очереди» отвечаются кодом из SQLite, без AI вовсе.

## 1. Текущая архитектура

```text
Telegram (супергруппа, топики)
    ↓
aiogram: два Dispatcher'а (dp_assistant, dp_workers), main.py
    ↓
bots/handlers.py — маршрутизация сообщений и callback_query
    ↓
bots/router.py — явное упоминание → топик → ключевые слова → Ассистент
    ↓
orchestrator/*.py — по одному модулю на роль
    ↓
orchestrator/agent.py — единственная точка вызова Anthropic API
    ↓
Anthropic API (claude-opus-5, output_config.effort, prompt caching)
```

### Семь Telegram-ботов, один процесс

`main.py` поднимает семь ботов одним процессом aiogram: `dp_assistant`
слушает сообщения и callback от имени Ассистента, `dp_workers` слушает
только `callback_query` от имени остальных шести (нажатия приходят тому
боту, который отправил кнопку). `bots/registry.py` держит все семь
`aiogram.Bot` и общую очередь отправки с троттлингом на `chat_id`
(Telegram-лимит ~20 сообщений/мин в один чат).

Процесс живёт под `launchd` (`space.lily.content-factory`), не под
демоном: нужен пользовательский сеанс, чтобы поднимался headless Chrome
для рендера макетов. Только один экземпляр — второй инстанс с тем же
токеном ловит `Conflict: terminated by other getUpdates`.

### Маршрутизация

`bots/router.py:resolve()` — четыре сигнала по приоритету: явное
упоминание бота → явные коллизии (`OVERRIDES`) → ключевые слова
(`TRIGGERS`) → топик по умолчанию (`TOPIC_DEFAULT`). Ничего не подошло —
уходит к Ассистенту. `bots/handlers.py` дополнительно проверяет пять
"ждёт правку" флагов (`wants_fix`/`wants_reason` на Стратеге, Редакторе,
Reels, Дизайнере, Публикаторе) **до** маршрутизации — иначе ответ на
кнопку "Правки" уезжает в общий разбор смысла и теряется.

### Вызов модели: `orchestrator/agent.py`

Восемь мест зовут модель: `unpack.py`, `refresh.py`, `research.py`
(все три — Ресёрчер/распаковка/правка профиля), `reply.py` (Ассистент),
`strategy.py` (Стратег), `editor.py` (Редактор), `reels.py` (Редактор
Reels), `design.py` (Дизайнер). Публикатор (`publisher.py`) модель не
зовёт вообще — намеренно, публикация детерминирована.

Системный промпт собирается `agent.build_system()` тремя блоками, от
стабильного к изменчивому, с точками prompt-кеша:

1. `roles/frame.md` + `roles/{role}.md` — одинаково у всех тенантов,
   кешируется и читается всеми.
2. Маска (только у Ассистента) + `Бренд: {name}` + секции профиля —
   стабильно внутри тенанта, кешируется на тенанта.
3. `extra` — контекст конкретного запроса, без точки кеша.

Порядок — не стиль, а деньги: любое изменение блока обесценивает кеш
всего, что идёт после него. `agent.ask()` дополнительно считает дневной
бюджет вызовов на тенанта (`llm_usage` в SQLite) и различает 4xx-отказ по
существу (нет средств, битый ключ — не повторяем) от временного сбоя
(429, 5xx — три попытки с экспоненциальной паузой).

Дизайнер — единственная роль без `profile=`: ТЗ площадки и эталонный
макет едут в некешируемом `extra`, и это самые дорогие вызовы завода.

### Хранение состояния — два контура

- **Горячее** — SQLite (`storage/db.py`): тенанты, топики, темы
  (`themes`, статусы `idea → draft → ready → pub` / `skip` / `failed`),
  публикации (`posts`, `external_id UNIQUE` — защита от дубля), метрики,
  очередь задач (таблица `tasks`, сейчас не используется активно ни одной
  ролью — задел на будущее), дневной бюджет вызовов (`llm_usage`).
- **Холодное** — файлы бренда через `storage/brand.py` (`Brand`/`Store`):
  `core.md`, `goals.md`, `platforms.md`, `sources.md` плюс артефакты
  (тексты постов, макеты, дайджесты). Версионируется git-коммитом при
  каждой записи (`Brand.write`), с защитой от коммита в чужой репозиторий
  выше по дереву (`_own_repo`).

Роли не трогают пути напрямую — только через `Brand`/`Store`. Общий
каркас роли (`orchestrator/desk.py`, класс `Desk` и функции `pick`,
`brand`, `profile`, `today`) вынесен из четырёх ролей, которые были
устроены одинаково: взять тему → позвать модель → показать карточку с
кнопками → пережить перезапуск процесса → принять правку.

### Детерминированные проверки — граница держит код, не промпт

- `validators/check_voice.py` — длинное тире, противопоставления
  «не X, а Y», усилители-пустышки, капслок, стоп-слова бренда. Находка —
  отказ, весь текст переписывается заново, не патчится.
- `validators/check_script.py` — то же для суфлёрного текста: цифра
  вместо слова, строка длиннее 40 знаков/7 слов, эмодзи, разметка,
  ремарки, сокращения, бюджет слов от хронометража.
- `orchestrator/strategy.py:_fit` — фильтрует ответ модели по факту:
  дата вне окна, второй пост в занятый слот, площадка не из набора,
  битый id из вольного текста — всё это код отбрасывает, а не молча
  принимает. Тот же принцип нужен любой следующей роли, которая отвечает
  структурой.
- `orchestrator/design.py:inspect()` — несуществующее фото, неверный
  холст, слова не из текста Редактора.

### Design-pack

`design-pack/` в коде — эталонные макеты и компоненты на CSS-переменных,
общие для всех тенантов. `design/` в папке бренда — токены, ТЗ площадок,
фото, специфичные для клиента. Рендер — headless Chrome с
`--virtual-time-budget` (шрифты едут с Google CDN, без этого флага Chrome
снимает кадр раньше, чем они догрузятся, и макет тихо уходит системным
шрифтом).

### Publisher — уже техническая автоматизация

Важная деталь для миграции: **Публикатор уже устроен ровно так, как
целевая архитектура просит устроить публикацию.** Он не зовёт модель,
собирает комплект детерминированно, проверяет потолки (1024 знака под
картинкой vs 4096 в тексте), защищён от двойной публикации
(`posts.external_id UNIQUE` + запись `sending` до отправки, не после).
Мигрировать здесь по сути нечего — разве что явно зафиксировать в новой
архитектуре, что Publisher не получает собственного `.claude/agents/*.md`
никогда.

## 2. Целевая архитектура

```text
Telegram Group
    ↓
Telegram bots (те же семь+один аккаунт, то же назначение UI)
    ↓
Python / aiogram (интерфейс, состояние, публикация — без изменений)
    ↓
Task / Claude Code Bridge  ← новый слой, ещё не существует
    ↓
Claude Code
    ↓
Assistant = Director (.claude/CLAUDE.md)
    ↓
вызывает Claude Code Subagents (.claude/agents/*.md)
    ↓
результаты возвращаются в Telegram через bridge
```

Python остаётся ответственным за Telegram, хранение состояния,
техническую автоматизацию и публикацию. Claude Code берёт на себя
понимание задачи, оркестрацию и производство контента. Разделение
проходит ровно там же, где сейчас разделены `orchestrator/*.py`
(суждение) и `validators/*.py` + `storage/*.py` (детерминированный код) —
это не новый принцип для проекта, а тот же самый принцип на новом слое.

### Чего архитектура не допускает

**Python не вызывает роли по очереди сам.** Вот эта схема запрещена, и
запрещена именно потому, что она соблазнительна:

```text
Python → Researcher API → Strategist API → Writer API
```

Так выглядит нынешний завод, и так же будет выглядеть половинчатая
миграция, где Python научился звать `claude -p`, но цепочку по-прежнему
задаёт сам. Внешне работает, а решение «кого звать» оказывается
размазано по двум слоям: часть в `bots/router.py` и `handlers.py`, часть
в `.claude/CLAUDE.md`. К третьей правке они разъедутся, и никто не
сможет сказать, где на самом деле выбирается workflow.

Выбор ролей целиком принадлежит Director внутри Claude Code. Python
передаёт задачу и забирает результат.

Обратная сторона того же правила: **не всякий запрос вообще требует
AI.** «Что сейчас в очереди» это `SELECT` к SQLite с точным ответом.
Такое не идёт ни через bridge, ни через прямой вызов модели — оно
отвечается кодом. Запрет выше про то, кто выбирает роли, а не про то,
что каждый запрос обязан куда-то поехать.

## 7. Решения, принятые при переносе промптов (этап 4)

Три решения, которые стоит понимать до того, как читать
`.claude/agents/*.md` — они объясняют, почему файлы выглядят короткими.

### Субагент это адаптер, поведение остаётся в `roles/*.md`

Каждый `.claude/agents/*.md` содержит: идентичность, откуда берётся вход,
куда пишется выход, какой код проверяет роль после — и **ссылку** на
`roles/frame.md` + `roles/{role}.md`, которые субагент читает на старте.
Сам текст промпта не копируется.

Причина прямо из журнала проекта: копии промптов и схемы уже были убраны
из спеки 16.08, потому что разъехались с оригиналом и успели соврать про
две роли. Второй набор копий воспроизвёл бы ту же поломку — с той
разницей, что теперь разъезжались бы не документация и код, а два
работающих промпта одной роли.

Побочный выигрыш: на этапе 8, когда старый API-слой начнут убирать,
`roles/*.md` не превращается в мёртвый код — он остаётся единственным
домом поведения ролей.

Это решение обратимо: если окажется, что чтение двух файлов на старте
мешает (например, субагент их игнорирует), содержимое можно свести в один
файл, оставив `roles/*.md` источником для генерации.

### Результат в двух формах, потому что читателей двое

Каждый артефакт в `tasks/{id}/` это markdown для человека **плюс** блок
JSON с машинным контрактом в схеме роли (`facts`/`mechanics`/`gaps` у
Ресёрчера, `text`/`checks`/`notes` у Writer и так далее — схемы не
менялись).

Так стадия 5 (ручная проверка без bridge) даёт человекочитаемый
результат, а стадия 6–7 переиспользует существующие парсеры и валидаторы
без переписывания: `agent.parse_json`, `strategy._fit`, `check_voice`,
`check_script` продолжают работать с теми же схемами.

### Валидаторы прогоняются дважды, и это не избыточность

Субагент прогоняет `check_voice.py` / `check_script.py` на себе — это
быстрая обратная связь, дешевле круга переделки. Python прогоняет их же
после субагента — это гейт.

Убрать внешний прогон и поверить субагенту на слово нельзя. Ровно на этом
проект уже обжигался: промпт это просьба, границу держит код. Формулировка
«я проверил, всё чисто» от роли, которая сама себя оценивает, ничем не
отличается от отсутствия проверки.

### Граница Стратег / Идеатор — решено 29.08

**Идеатор забирает раскачку целиком.** Стратег держит только скелет:
слот, рубрика, `goal`, `funnel_stage`, `why`, рабочий заголовок и хук.
Таблица «Углы и заряды», список зарядов и поле `variants` — работа
Идеатора.

За основу взят скилл `lily-creative-producer` из личного набора владельца
проекта, целиком: три захода на тему с разным углом, зарядом и хуком;
скоринг; спор Продюсер против Скептика с обязательным вердиктом; плюс
две-три темы сверх плана. Роль проверенная, переносить дешевле, чем
изобретать.

Два отличия от скилла, продиктованные состоянием завода:

- **Скоринг помечен как оценка, а не измерение.** Метрик по факту
  публикации у завода нет (снимки 24 ч / 72 ч / 7 д не снимаются, в
  `posts` пусто), поэтому «скоринг по своей статистике» опирать не на
  что. Выдуманное измерение живёт месяцами и выглядит согласованным.
- **Слот Идеатору не принадлежит.** Дата и площадка приходят от Стратега
  уже проверенными `_fit`; менять их нельзя, иначе тема отвалится на
  следующей проверке или встанет вторым постом в занятый день.

Роль оформлена как полноценный житель завода: промпт в `roles/ideator.md`
рядом с шестью остальными, адаптер в `.claude/agents/ideator.md`. Так она
доступна и старому пути через `orchestrator/`, если он понадобится, и не
остаётся артефактом, существующим только внутри Claude Code.

### Долг, который надо закрыть: раздел «Углы и заряды» в двух местах

`roles/strategy.md` пока **всё ещё содержит** раздел «Углы и заряды» и
инструкцию заполнять `variants` — файл переписывается прямо сейчас (v2.0,
незакоммиченная работа), и трогать его в этой миграции было бы правкой

Противоречие снимает явный блок-исключение в
`.claude/agents/strategist.md`.

**Закрывать этот долг можно только на этапе 8, не раньше.** Первая

альтернатива — регресс в том, что работает.

## 9. Технический spike: запуск Claude Code из Python (29.08)

Проведён дважды: до входа в CLI и после. Инструмент: `deploy/spike-bridge.py`. Это **не bridge**, а воспроизводимый
замер — чтобы ограничения были доказательством, а не мнением. Повторить:

```bash
./.venv/bin/python deploy/spike-bridge.py --live
```

### Методологическая оговорка, без неё замер врёт

Скрипт, запущенный из сессии Claude Code, отдаёт подпроцессу по
наследству `CLAUDECODE=1`, `CLAUDE_CODE_ENTRYPOINT=claude-desktop`,
`CLAUDE_CODE_MESSAGING_SOCKET`, `CLAUDE_CODE_MESSAGING_TOKEN` и ещё три.
Завод под `launchd` не получит ни одной из них. Мерить в унаследованном
окружении значит измерить собственную среду вместо целевой, поэтому
`clean_env()` собирает окружение белым списком: `PATH`, `HOME`, `USER`,
`LANG`, `LC_ALL`, `TMPDIR`, `SHELL` плюс то, что передано явно.

Все числа ниже сняты в чистом окружении.

### Авторизация: что работает, что нет

Замерено дважды: **до** входа в CLI и **после**. Второй замер сделан из
обычного терминала, вне сессии Claude Code, поэтому наследования
`CLAUDE_CODE_*` не было вовсе.

| Способ | До входа | После входа |
|---|---|---|
| Чистое окружение, без ключа | ✗ `Not logged in`, 2.2 с | ✓ **работает, 6.6 с** |
| Чистое окружение + `ANTHROPIC_API_KEY` | ✓ работает, 4.1 с | ✓ работает, 4.7 с |
| `~/.claude/.credentials.json` | нет | нет |
| Keychain `Claude Code-credentials` | нет (`exit 44`) | **есть (`exit 0`)** |

**Подписочный путь работает.** Разовый `claude` → `/login` в терминале
кладёт учётные данные в Keychain, и подпроцесс берёт их оттуда сам:
`ANTHROPIC_API_KEY` в окружении bridge **не нужен**. Файла
`~/.claude/.credentials.json` при этом не появляется — на macOS хранилище
это Keychain, и проверять надо именно его.

**Существующая авторизация Claude Code подпроцессу недоступна, и причина
не в правах.** У CLI на этой машине **нет собственных сохранённых
учётных данных вообще**: ни файла, ни записи в Keychain. Сессия, в
которой шла разработка, авторизована хостом — desktop-приложением, через
`CLAUDE_CODE_MESSAGING_SOCKET` и токен в окружении. Это брокерская
авторизация на процесс, она не лежит на диске и не наследуется свежим
`claude -p`.

Оба пути рабочие, выбран первый:

1. **Вход CLI (подписка).** Ключ в окружении не нужен. Bridge просто не
   передаёт `ANTHROPIC_API_KEY`, и CLI берёт учётные данные из Keychain.
   **Это снимает зависимость от баланса API** — того самого, из-за
   которого завод простаивал и из-за которого в живой сводке 16.08 пустой
   раздел наблюдений.
2. **`ANTHROPIC_API_KEY` в окружении.** Работает, остаётся запасным. Он
   уже есть у проекта и нужен нынешнему `orchestrator/agent.py`, который
   мы не трогаем.

**Чего этот замер не доказал.** Проверена **авторизация**, а не
тарификация: без ключа вызов проходит, значит идёт по учётным данным
входа. Куда именно списывается потребление — в лимиты подписки или в
API-кредиты — из вывода CLI не видно. `total_cost_usd` в ответе
ненулевой ($0.109), но на подписке это оценка «во что обошлось бы по
API-тарифу», а не счёт. Подтвердить может только человек, посмотрев
потребление на `console.anthropic.com` после нескольких прогонов.
Практическая разница: на подписке ограничение это лимиты и их окна, а не
остаток на балансе.

**Под `launchd` подписочный путь нужно проверить отдельно.** Агент
стартует без терминала, а Keychain может потребовать разблокировки или
отдать отказ неинтерактивному процессу. Замер выше сделан из терминала,
где сеанс уже разблокирован, и на агента он не переносится. Если под
`launchd` Keychain откажет, запасной путь — ключ в окружении, который
предсказуем, но возвращает зависимость от баланса.

### Необходимые переменные окружения

Минимум для работающего вызова: `PATH` (найти бинарь), `HOME` (найти
`~/.claude`) и **один** из способов авторизации выше.

`ANTHROPIC_BASE_URL` в чистом окружении не нужна: без неё CLI идёт на
`https://api.anthropic.com`. В сессии разработки она задана явно тем же
значением, так что прошлые замеры шли в настоящий API, а не через
локальный прокси.

### Стоимость холодного старта — главное ограничение

Один и тот же вырожденный запрос («ответь одним словом: ок»),
`--output-format json`, `num_turns: 1`:

| Где запущен | Стоимость | Задержка |
|---|---|---|
| Вне проекта | **$0.042** | — |
| В корне завода, по ключу | **$0.130** | 4.1–4.7 с |
| В корне завода, по подписке | **$0.109** | 6.6–7.0 с |

Разница около $0.08 — это наш контекст: `CLAUDE.md` проекта,
`.claude/CLAUDE.md` и описания шести субагентов, которые грузятся на
**каждый** вызов. Пол при любой задаче — порядка одиннадцати центов
API-эквивалента, до того как сделана хоть какая-то работа.

**Второй пол, про который легко забыть: задержка 5–7 секунд.** Это тоже
холодный старт, и он не зависит от сложности задачи: вырожденное «ответь
одним словом» отвечалось 6.6 секунды. Для задачи «собери план недели» это
незаметно, для реплики в чате это пауза, после которой человек считает,
что бот сломан. У проекта уже записан урок «молчание неотличимо от
поломки», и здесь он попадает точно в разговорный контур.

На подписке денежный пол перестаёт быть главным ограничением: считаются
лимиты и их окна, а не остаток баланса. Задержка при этом никуда не
девается и остаётся аргументом при решении по `reply.py`.

Это обратная сторона того, что архитектура выигрывает в другом. Нынешний
`agent.build_system()` кладёт точки prompt-кеша так, что `frame.md` плюс
роль читаются из кеша примерно за десятую часть цены, и стабильный
префикс общий для всех тенантов. Bridge каждый раз стартует холодным:
кеш между отдельными процессами `claude -p` не переиспользуется.

Прямое следствие для архитектуры, не для бухгалтерии:

**Через bridge должны идти только задачи, которые оправдывают холодный
старт.** Это оркестрация нескольких ролей: план недели, полный пакет
контента, раскачка тем.

Ответ на «что сейчас в очереди» и «когда выходит X» через bridge пускать
нельзя, и не только из-за цены: **это вообще не задача для AI.** Запрос к
SQLite, у которого есть точный ответ, не нуждается ни в Claude Code, ни в
прямом вызове модели. Такие вопросы должны отвечаться кодом.

**Судьба разговорного контура `reply.py` — открытый вопрос, а не
решение.** Первая редакция этого раздела предлагала оставить его на
прямом API навсегда; это было преждевременно, замеров под такой вывод
нет. Решать после проверки подписочного входа, и вот по каким данным:

- работает ли `claude -p` по подписке из чистого окружения;
- какая при этом реальная стоимость и какие лимиты;
- годится ли он по задержке для разговорного запроса, где человек ждёт
  ответа в чате, а не результата работы;
- насколько стабильно это держится под Telegram-нагрузкой.

Целевая архитектура остаётся прежней: Python это Telegram и
инфраструктура, Claude Code это рассуждение и оркестрация. Гибрид
допустим, если замеры покажут, что он существенно лучше, — но как
измеренный выбор, а не как остаток недоделанной миграции.

### Машинный вывод пригоден

`--output-format json` разбирается и отдаёт то, что нужно bridge:
`session_id`, `total_cost_usd`, `num_turns`, `is_error`, `duration_ms`,
`modelUsage`, `api_error_status`. Стоимость каждой задачи можно писать
рядом с ней и видеть, во что обходится неделя.

### Субагенты видны из подпроцесса

Свежий `claude -p` в корне проекта в чистом окружении видит все шесть
файлов `.claude/agents/` и подхватывает `.claude/CLAUDE.md`. Прямого
вызова конкретного субагента снаружи нет: оркестрация идёт через
рассуждение Director, как и зафиксировано в целевой архитектуре.

### Как безопасно запускать из Python

Пять правил, реализованных в `run_claude()` спайка:

- **`argv` списком, без `shell=True`.** Текст человека из Telegram
  попадает в аргумент процесса, а не в строку шелла, и выйти из неё не
  может. Это единственный пункт здесь про безопасность в узком смысле,
  и он не обсуждается.
- **`env` собирается белым списком**, а не наследуется. Иначе в
  подпроцесс уедет всё, что оказалось в окружении бота, включая токены
  восьми ботов из `.env`.
- **`cwd` задан явно.** От него зависит, какой `CLAUDE.md` и какие
  субагенты подхватятся.
- **`timeout` обязателен.** Без него зависший вызов держит задачу вечно,
  а человек в Telegram видит молчание — «молчание неотличимо от поломки».
- **`stdout`/`stderr` захвачены.** Ничего не утекает в лог процесса,
  ошибка возвращается кодом и текстом, а не теряется.

Отдельно: `--allowedTools` сужает набор инструментов до нужных роли.
Разрешать всё подряд процессу, который принимает текст из чата, не
нужно.

## 10. MVP для локальной разработки

Минимальный работающий контур, который проверяет схему целиком и **не
трогает** существующий API-слой. Строится после того, как выбран способ
авторизации.

```text
Telegram: человек ставит задачу
    ↓
Python: создаёт tasks/{id}/input.md и запись в таблице tasks
    ↓
Python: claude -p подпроцессом, чистое окружение, cwd = корень проекта
    ↓
Claude Code: Director читает input.md, выбирает минимальный workflow
    ↓
Director: зовёт нужных субагентов, они пишут артефакты в tasks/{id}/
    ↓
Python: читает final.md и status.json, обновляет запись задачи
    ↓
Telegram: результат уходит человеку от лица нужной роли
```

### Что делает Python и чего не делает

Делает: принимает сообщение, заводит задачу, запускает процесс, читает
файлы, отправляет результат, публикует. Не делает: **не решает, каких
субагентов звать.** Эта развилка целиком внутри Claude Code, иначе
оркестрация расползётся по двум слоям и разъедется.

### Границы MVP, которые надо назвать заранее

- **Один тенант.** Мультитенантность требует отдельной папки задач и
  отдельного `cwd` на бренд; в MVP это лишнее.
- **Одна задача за раз, без очереди.** Таблица `tasks` в SQLite уже есть
  и не используется — её хватит как журнала. Настоящая очередь строится,
  когда станет ясно, сколько задача занимает.
- **Один workflow из конца в конец.** Разумный первый — «сделай план
  недели»: он задействует три роли, даёт проверить и выбор цепочки, и
  передачу артефактов, и не пишет ничего в живой канал.
- **Прогресс в чат не течёт.** Человек видит «принял» и потом результат.
  Промежуточные сообщения от лица ролей это следующий шаг, и он потребует
  `--output-format stream-json`.
- **Старый путь остаётся рабочим.** Bridge включается на одну задачу,
  всё остальное продолжает идти через `orchestrator/agent.py`. Сравнивать
  результаты можно только так.

### Порядок сборки

1. Выбрать авторизацию: проверить путь 2 (вход CLI по подписке), иначе
   остаться на `ANTHROPIC_API_KEY`.
2. `bridge.run(task_id)` — тонкая обёртка над `run_claude()` из спайка:
   создать папку, записать `input.md`, вызвать, прочитать результат.
3. Подключить **одну** точку входа в `handlers.py` — например, фразу
   «собери план через Claude Code», чтобы старый путь остался рядом и
   работал.
4. Прогнать на живом бренде, сравнить с тем, что даёт нынешний Стратег.
5. Записать стоимость и время задачи в `tasks`, посмотреть на неделе.

Снимать старый слой можно только после пункта 5, и по одной роли.

## 11. Что показали живые прогоны (этап 6, 30.08)

Пять прогонов до первого удавшегося. **Ни одну из трёх поломок стенд
поймать не мог**: все три про поведение Director внутри headless-процесса,
а не про код моста. Код как раз отработал верно — отказ записан, стоимость
снята, задача не задвоилась.

| Задача | Исход | Время | Оценка $ | Что вскрыла |
|---|---|---|---|---|
| `plan-01` | failed | 81 с | 0.78 | лимит запросов, до работы не дошло |
| `plan-02` | failed | — | — | процесс убит снаружи, строка осталась `running` |
| `plan-03` | failed | 275 с | 0.93 | фоновый субагент умирает вместе с процессом |
| `plan-04` | timeout | 900 с | — | потолок был угадан, а не посчитан |
| `plan-05` | **done** | 911 с | 2.98 | — |

### Фон в headless-режиме смертелен

`plan-03` запустил Ресёрчера **в фоне**, попробовал дождаться его через
планировщик пробуждений и трекер задач, не смог и закончил ход фразой
«подхвачу, когда ресёрчер закончит». В `claude -p` конец хода это конец
процесса: фоновый субагент умер вместе с ним, будить было некого. 275
секунд, около доллара, ноль артефактов.

Правило записано в `.claude/CLAUDE.md`: субагентов звать синхронно
(`run_in_background: false` — у `Agent` фон включён по умолчанию), ход не
заканчивать, пока не написан `final.md`. В `plan-04` правило подействовало
с первого раза.

### Потолок надо считать, а не округлять

Замер по транскрипту `plan-04`: разведка минуту, Ресёрчер **девять минут
сорок пять секунд** живых запросов по девяти внешним каналам, следом
Стратег — и его срезало на середине. Удавшийся `plan-05` занял **911,5 с**,
то есть под прежним потолком в 900 с он бы тоже умер, и разница между
«не работает» и «работает» составила одиннадцать секунд.

Потолок поднят до 1800 с. Если workflow станет длиннее трёх ролей, считать
заново — и снова замером.

### Провал обязан называть то, что успел сделать

`plan-04` к моменту смерти уже положил `research.md` на 16 КБ. Человек об
этом не узнал: мост сказал только «не уложился в 900 с». Девять минут
живой работы остались невидимыми — такую работу заказывают заново.
`_fail` теперь перечисляет легшее на диск, `input.md` за достижение не
считая: его положил Python, а не роль.

Туда же ушла последняя реплика Director из JSON CLI. Без неё причину
`plan-03` пришлось искать в транскрипте сессии, хотя она была в одном
предложении.

### Доллары в журнале — это не деньги

Число `estimated_api_cost` легко прочитать как счёт. Счётом оно не
является, и путать это дорого — на нём будут строить решение, включать ли
авто-режим.

Проверено на этом же прогоне, а не выведено из документации:

- в окружении подпроцесса **нет** `ANTHROPIC_API_KEY` (`clean_env` отдаёт
  ровно `HOME`, `PATH`, `SHELL`, `TMPDIR`, `USER`), при том что в
  окружении самого бота ключ есть — его кладёт `load_dotenv`;
- пять прогонов при этом отработали, то есть подпроцесс авторизовался
  входом CLI из Keychain, а не ключом;
- в транскрипте сессии лежат **токены**, а не деньги. Доллар выводит сам
  CLI, умножая токены на прайс-лист API.

Значит `$2.98` у `plan-05` читается так: «столько стоил бы этот прогон,
если бы шёл по API-тарифу». Фактически израсходованы **лимиты подписки**,
а не средства. Поэтому и колонка названа длинно, и Публикатор от баланса
не зависит: у нового пути зависимости от баланса API нет вовсе.

Что из этого всё-таки полезно: **относительная** величина. Удавшийся
прогон это ~$3 API-эквивалента против $0.11 холодного старта из раздела 9,
то есть двадцать семь холодных стартов. Делает эту разницу Ресёрчер с
живыми запросами, а не запуск процесса. Для планирования нагрузки годится,
для бухгалтерии — нет.

**Журнал занижает и эту оценку.** У прогона, убитого по потолку, JSON от
CLI не приходит вовсе, поэтому у `plan-04` поле пустое — хотя пятнадцать
минут работы были настоящими. Пункт 5 раздела 10 надо читать с поправкой:
там копится оценка нагрузки, а не расход.

### Мост пошёл на Sonnet 5, старый путь ходит на Opus 5

В сессии `plan-05` все 45 сообщений — `claude-sonnet-5`. Старый путь берёт
модель из `config.py`: `ANTHROPIC_MODEL`, по умолчанию `claude-opus-5`.

Это ломает приёмку этапа 7 в её нынешней формулировке. «Прогнать один
workflow параллельно со старым путём и сравнить» перестаёт сравнивать
архитектуры, как только модели разные: разницу в плане нельзя будет
отнести ни к оркестрации, ни к промптам, ни к модели — она размазана по
всем трём.

Перед этапом 7 надо решить явно: либо мост ходит на той же модели, что и
старый путь (тогда сравнение честное), либо смена модели признаётся частью
миграции и записывается в журнал решений — но тогда сравнение делается на
одинаковой модели **отдельно**, а не заодно.

Замечание не гипотетическое: `plan-05` собрал содержательный план, и
соблазн принять его как доказательство «новый путь не хуже» велик именно
потому, что результат хороший.

### Мелочь, замеченная и не исправленная

Director правит `input.md`, дописывая туда контекст для субагентов. Файл
задумывался как контракт Python → Director и правиться не должен. Вреда
нет, провенанс мутнеет. Чинить, когда появится вторая точка входа кроме
`/plan`.
